## 8. Exact rollback runbook — local verification only

On a guard failure/timeout before COMMIT, stop; the migration's transaction (or M's
required runner transaction) leaves that step unapplied. Verify catalog/ACL state
and history before deciding anything else. Prefer fixing a service configuration/
code issue while retaining restricted grants. Rolling application code back to
e634610 with a verified service key may need no SQL rollback.

If metadata rollback is explicitly approved, take a fresh backup/snapshot, pause
administrative writes and compare prior ACLs against section 2. Use the exact
prepared files below, only for the steps actually applied and in reverse order:

1. **tests/security/rollback-businesses.sql**: B reversal. Disables business RLS
   and restores inspected client/service ALL plus sequence ALL, PUBLIC none.
   Use only if complete baseline reversal is required; it exposes provider fields
   and permits cross-tenant direct writes again. Retaining RLS with service grant
   repair is preferred if the failure is confined to service privileges.
2. **tests/security/rollback-salons.sql**: S reversal. Restores inspected ALL to
   anon/auth/service, PUBLIC none; does not change RLS or rows. Reintroduces legacy
   direct client read/write exposure.
3. **tests/security/rollback-memberships.sql**: M reversal, after B. Drops only the
   new named FK; restores the prior column comment and SELECT/TRUNCATE/REFERENCES/
   TRIGGER/MAINTAIN client grants, service ALL; leaves existing membership RLS,
   policy, unique/Auth FKs and all rows intact. Allows orphan membership creation
   and authenticated/anon TRUNCATE privilege again.

Each rollback file is transactional with 5-second lock/30-second statement bounds.
Invoke with psql -X -v ON_ERROR_STOP=1 -f and the explicitly approved connection.
Do not use DROP CASCADE, recreate tables, reset sequences, restore old business
data wholesale, remove customers, or delete/assign salon rows.

After **each** reverse step, run rollout-checks.sql and require:

- B reversal: business RLS=false/FORCE=false, zero policies; target grants equal
  section 2 and sequence name/ACL unchanged. Service/API reads still work.
- S reversal: salon grants equal section 2; RLS=false; row count and chichi/chi
  marker equal the just-captured pre-rollback values, not an assumed historic count.
- M reversal: named FK absent, previous comment restored; own-active SELECT policy
  unchanged; Auth FKs/unique checks retained; membership row counts/IDs identical
  to the pre-rollback snapshot; orphan count remains zero.
- All: business rows/customer data unchanged; no new dependency/grant drift.

The disposable test compares row JSON internally (synthetic only) and exact ACL/
RLS/comment snapshots. Both new and legacy salon rows, and memberships, survive.
Data already intentionally deleted via CASCADE before rollback cannot be recovered
by dropping the FK; use verified backups and a separate approved recovery if that
ever occurs. This audit performed no production deletion.

Do not silently delete/edit production migration history. Record rollback and
future compensation through the approved release process; after M reversal, its
recorded historical version may require a newly reviewed forward repair rather
than blind replay. Local harness has no production migration-history side effects.
